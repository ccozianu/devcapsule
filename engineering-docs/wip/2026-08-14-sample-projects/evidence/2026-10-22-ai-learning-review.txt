I am Claude Fable 5.1 (model ID claude-fable-5-1). This is a static read of the repository only. Dependencies are not installed in this worktree, so I did not run the tests or the type check, and I did not touch any environment variable, secret file, or external service.

Overall the design is sound. State, nonce and PKCE are bound to the browser by a signed HttpOnly cookie, tokens are stored hashed, codes are HMAC-keyed, single-use consumption is atomic, errors are scrubbed, and the allowlist fails closed. The findings below are real but none is a critical break. Ordered by priority.

**1. Password setup refreshes its own "recent Google login" window.** `src/app.ts:110` issues a brand-new session typed `GOOGLE` with a fresh `createdAt` after every setup. The ten-minute check at `src/app.ts:101` therefore passes again immediately, so one fresh Google session can change the password indefinitely, and a stolen session that was once fresh stays "fresh" as long as the holder keeps re-running setup. Fix: carry the verified Google session's original `createdAt` into the replacement session, or record a separate `authenticatedAt` that setup never renews.

**2. Account lockout never recovers on its own and is a cheap denial of password sign-in.** At `src/app.ts:119-124` the lock is checked only after the Argon2 verify, the failure counter is reset only inside `issueSession`, and nothing clears the counter when `lockedUntil` passes. After one lockout, every later wrong guess re-locks for fifteen minutes, and a correct password on an unremembered browser does not reset it until the email code is confirmed. Fix: check `lockedUntil` before hashing, reset `passwordFailures` and `lockedUntil` as soon as a correct password is verified, and treat an expired lock as a zeroed counter.

**3. Username collision on setup surfaces as a 503.** A second user choosing an existing username trips the unique index in the transaction at `src/app.ts:104`, and the generic handler at `src/app.ts:61` turns that into "Request could not be completed." The transaction rolls back, so nothing is corrupted, but the user cannot tell what went wrong. Fix: pre-check or catch Prisma error code P2002 and return a 409 with a fixed "username unavailable" message.

**4. One secret serves two purposes.** `AUTH_SECRET` signs the OAuth cookie via `@fastify/cookie` at `src/app.ts:26` and keys the challenge HMAC at `src/security.ts:5`. This is not exploitable today, but a future leak of either use compromises both. Fix: derive two subkeys with HKDF and distinct labels.

**5. Per-IP rate limits collapse behind any proxy.** With `trustProxy: false` at `src/app.ts:25`, Vite in development and any reverse proxy in production present one client address. The 10-per-15-minute buckets on the auth routes then apply to everyone combined, which makes sign-in trivially blockable. The README already defers this to deployment work, so this is a confirmation that the gap is real, not a new finding.

**6. Challenge binding is a bearer capability, not a browser binding.** The challenge ID returned at `src/app.ts:138` is a random UUID and the only link between the password proof and the confirm step. Anyone holding ID plus code can confirm from any browser and mint a 30-day trusted device there. The ID has 122 random bits and is never placed in a URL, so this is acceptable, but if you want strict binding, store a hash of a short-lived HttpOnly "pending" cookie on the challenge row and require it at confirm.

**7. The db-apply script gives a misleading message when the confirmation flag is missing.** `scripts/db-apply.ts:7` throws an empty error, and the shared catch prints advice about connectivity and permissions. Print a specific "pass --confirm-initial-schema" message before any connection attempt. Secret handling in both scripts is correct: no DSN is built, raw errors are suppressed, and the SQL generator runs Prisma with a stripped environment.

**Things I checked that are correct:** state and nonce comparison, PKCE verifier handling, `email_verified` and audience checks, refusal to auto-link by email, session rotation on every login, revocation of sessions, devices and challenges on password setup and on "forget browsers", atomic attempt counting with the `attempts < 5` and expiry predicate, single-success enforcement via the delete count at `src/app.ts:148`, Origin enforcement on all mutations including GraphQL, `__Host-` prefixes under HTTPS, constant-time hash comparison, and the error handler never serializing provider or database errors. The migration SQL matches the schema.

**Test gaps worth closing before live acceptance:** no test exercises nonce mismatch or an unverified email in the callback, the lockout path, the successful setup path and its revocations, or the `/graphql` Origin check. The twelve tests present do cover the fail-closed allowlist, anonymous denial, cross-origin rejection, error scrubbing, code single-use, device ownership and the recent-Google-session rule.

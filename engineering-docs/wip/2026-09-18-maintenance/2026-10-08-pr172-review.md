## Findings and corrections

The performance approach is sound within its stated warm-cache scope: attach
directory sources directly, reuse the main context path, and retain extracted
archives at stable paths. Contribution stages and final `COPY --link` exports
already existed; this PR changes how their local inputs reach BuildKit.

The new unpack cache needed three corrections:

1. **Concurrent cache publication can destroy another caller's input.**
   The original helper reads a missing marker, then removes the destination
   without a lock. Another process can publish between those operations, and
   the delayed caller then deletes the completed tree while its owner may be
   building from it. Within one process, callers also share the PID-based
   staging name and can delete each other's extraction. Formation locks do
   not protect this: different formations share the same archive cache key.
   A lock for each archive digest now covers the complete read/recover/unpack/
   publish operation, including hits. Different digests remain independent.
2. **A completion record was accepted without establishing completion.**
   The old reader ignored schema and digest and accepted an absolute root,
   a root symlink outside the cache entry, or a missing installation directory.
   Reuse now requires a supported record for this digest and an existing
   directory contained in the cache entry. Invalid entries are reconstructed
   from the verified archive; removing a replaced entry does not follow its
   root symlink. This is structural validation, not re-hashing the tree.
3. **Failed and interrupted extraction leaked staging directories.**
   Exceptions left `.partial-<pid>` trees behind. A later launcher has another
   PID, so retrying did not recover them. A fixed `.partial` path is safe under
   the digest lock, is removed after ordinary failure, and is replaced by the
   next caller after an abrupt exit. Existing legacy PID-named leftovers are
   not pruned; this review does not introduce a cache-reaping policy.

The implementation names those invariants in the helper's docstring and gives
entry removal and marker validation their own small functions. It preserves the
published cache layout, digest keys, completed-tree marker format and named
context construction. It reuses the materializer's existing file-lock helper.

seven failing cases and five passing controls. The failures reproduce a

## Limits retained

- The 3.69 GB to 1.29 MB transfer and 21 s to 1.1 s measurements are Fable's
  recorded experiment. This review did not repeat a Docker benchmark or claim
  new IDE/end-to-end acceptance.
- Completed trees are assumed immutable in the developer-owned cache. Marker
  validation cannot detect modified or deleted files inside an otherwise valid
  root. Cache content hashing, pruning, and Docker-only installed-component
  reuse remain outside this change.
- A digest identifies one extraction layout. Current surface and ancillary
  callers must not interpret the same archive through incompatible extractors;
  a future general-purpose cache would need layout/version in its key.
- A named context must remain unchanged while Docker consumes it. The builder
  lock protects the shared main context, while the unpack lock prevents cache
  writers replacing a valid completed tree. External cache edits are not locked.
